# 拆解《云灯》：一个网页游戏是怎么跑起来的

打开 `E:\project\aigames\云灯\云灯.html` 对照着看。全文只有一个文件：HTML 骨架 + 两段 script
（第一段 `CORE` 管数值/存档/剧情/音频，第二段管玩法与渲染）。

> 行号对应 2026-11-19 这一版，之后只要改代码就会整体漂移。
> 别死记行号，**用函数名去搜**：`grep -n "function stepRun" 云灯.html` 之类，一步到位。
> 两个闭包之间的调用关系（谁挂在 `window` 上）见 `05-进阶地图.md` 的「坑六」。

## 一张图看懂

```
   ┌────────────────────────────────────────────┐
   │ DOM 层：标题 / 剧情 / 升级 / 结算 / 结局 浮层  │  ← 用 HTML+CSS 做，比画在 canvas 里省事
   ├────────────────────────────────────────────┤
   │ Canvas 层（720×1280 虚拟坐标）               │
   │   静态层：夜空、星、云海、岛（预渲染一张图）   │  ← 只画一次，存在离屏 canvas
   │   动态层：灯塔光束、下落物、玩家、粒子        │  ← 每帧重画
   │   HUD：夜数、灯芯、进度条、连击              │
   ├────────────────────────────────────────────┤
   │ 逻辑层（不画东西）                            │
   │   newRun() → stepRun(dt) → 判定/计分 → 状态机 │
   └────────────────────────────────────────────┘
```

关键认知：**渲染和逻辑是两套东西**。`stepRun` 只改数字（位置、血量、分数），
`drawScene` 只读数字画图。两者唯一的桥是「每秒 60 次、每次传一个 `dt`」。

## 机制 1：虚拟坐标 + 等比缩放

画布内部永远按 `720 × 1280` 算，外层 CSS 用 `aspect-ratio:9/16` 撑满屏幕。
好处：你在 4K 显示器和你手机上看到的构图一模一样，代码里所有坐标都是死数，不用算。

代价：手指位置要换算回虚拟坐标。这样写（`toVX`）：

```js
function toVX(clientX){
  var rect = cv.getBoundingClientRect();
  return ((clientX - rect.left) / rect.width) * W;
}
```

这是所有 2D 网页游戏的第一步，做错这一步会出现「手指在左边、灯笼在中间」的经典 bug。

## 机制 2：主循环与 dt

```js
function loop(ts){
  var dt = Math.min(.05, (ts - last) / 1000);
  last = ts;
  stepRun(run, dt, run.target);   // 逻辑
  drawScene(run, dt);             // 渲染
  requestAnimationFrame(loop);
}
```

三个要点：

1. **所有位移都乘 `dt`**：`o.y += o.vy * dt`。这样 144Hz 和 60Hz 的屏幕上速度一致。
2. **`dt` 封顶 0.05 秒**：切到后台再回来时，浏览器会给你一个巨大的 `ts` 差值，
   不封顶就会「物体瞬移到屏幕外」，玩家一回来就死。
3. **游戏暂停 = 停止调用 stepRun**，而不是把画面清空。所以暂停后画面还停在原处。

## 机制 3：掉落物生成（第 847 行 `spawn`）

```js
r.spawnT -= dt * 1000;                       // 用毫秒当计时器
if(r.spawnT <= 0){
    spawn(r);                                 // 生成一个
    r.spawnT = r.cfg.interval * (.86 + r.rng() * .3);   // 下一次间隔有 ±15% 抖动
}
```

为什么要抖动？因为固定间隔会让玩家在 10 秒内摸清节奏，然后游戏就变成背谱。
`±15%` 的抖动刚好让人「感觉得到节奏但抓不准」。

生成什么靠权重表：普通光屑、稀有「心焰」、稀有「记忆」、黑雾。每夜的权重都不同：

| 夜 | 时长 | 生成间隔(ms) | 下落速度 | 黑雾占比 | 记忆出现时机 |
| --- | --- | --- | --- | --- | --- |
| 1 | 42s | 640 | 210–250 | 3.5% | 62% |
| 2 | 45s | 610 | 225–268 | 5.5% | 60% |
| 3 | 47s | 575 | 240–286 | 7.5% | 58% |
| 4 | 50s | 540 | 256–300 | 8.5% | 56% |
| 5 | 52s | 505 | 272–318 | 10.0% | 54% |
| 6 | 55s | 470 | 286–330 | 11.0% | 52% |
| 7 | 60s | 440 | 298–342 | 14.5% | 50% |

这张表就是游戏的「难度曲线」本身。调难度不是改血量，是改这张表。

## 机制 4：接住判定——这一款最值得学的设计（第 976–980 行）

```js
if(o.y >= CATCH_Y && o.y <= CATCH_Y + 92){
    var dx = Math.abs(o.x - r.px);
    // 接光看光域（灯罩升级放大），受伤只看身体（身体窄，才躲得开）
    var reach = o.type === 'dark' ? 52 : limit;
    if(dx <= reach + o.r * .5){ ... }
}
```

一开始我把「接光」和「受伤」用同一个宽度判定，结果很荒谬：
玩家花钱升级灯罩（本意是变强），反而更容易被黑雾撞死。

于是拆成两个判定：

- **接光**用 `limit`（光域半径，灯罩升级会放大）→ 升级 = 更容易接住，是纯收益。
- **受伤**用固定 52px（身体半径）→ 升级不会让你更容易死。

这个改动教会我一件事：**判定框是设计语言，不是技术细节**。
同一个数字同时管「奖励」和「惩罚」，玩家一定会找到反直觉的漏洞。

## 机制 5：黑雾追光——为什么限定在 y∈(480,820)（第 969–972 行）

```js
if(o.type === 'dark' && o.y > 480 && o.y < 820){
    var pull = r.homing * (o.y / H) * dt;
    o.x += (r.px - o.x) > 0 ? Math.min(pull, r.px - o.x) : Math.max(-pull, r.px - o.x);
}
```

黑雾会朝玩家水平漂移，但**只在中段追**，快接近灯口时锁定方向。

我最初让它全程追，结果是「躲不掉」——你往左闪，它跟着往左，玩家只能干挨。
改成「中段追、最后 250px 锁定」之后，正确的操作变成**最后一刻侧闪**：
等它快落下来时再横移，它已经来不及跟了。这就是「留出可解窗口」。

一条可复用的经验：**任何追你的东西，都要在某个时刻放弃追踪**，否则它就不是敌人，是审判。

## 机制 6：反馈层——手感是叠出来的

- **粒子**：接住时溅 6–10 个亮点，寿命 0.4 秒。
- **飘字**：`+1`、`+2`、`灯芯 −1`，往上飘 36px 后淡出。
- **震屏**：受伤时 `shake` 值拉满，每帧衰减，绘制前 `translate` 一个随机偏移。
- **闪屏**：受伤时整屏叠一层紫色，透明度随 `flash` 衰减。
- **光晕**：所有发光物体都用**预生成的径向渐变贴图**缩放绘制，不用 `shadowBlur`
  （`shadowBlur` 每帧重算，是网页游戏最常见的性能杀手）。

音效用 Web Audio 现场合成，一个音都没有下载：

```js
// 接住：短促三角波，音高随连击升高
osc.type = 'triangle';
osc.frequency.value = 520 + Math.min(streak, 12) * 18;
```

连击越高音越高，玩家不用看数字就知道自己「在状态里」。这是最便宜的正反馈。

## 机制 7：存档与流程状态机

存档就是一个对象，`JSON.stringify` 进 localStorage（第 384 行 `save`）：

```js
{ night: 3, shards: 120, best: 41, up:{oil:2,shade:1,hand:1}, seenEnding: false, cleared: false }
```

流程状态机：`title → story(n) → play(n) → result(n) → upgrade → story(n+1) … → ending`。
每个状态只有一个「下一步」，所以不会出现点了按钮没反应的情况。

## 机制 8（最特别的一节）：没有真人也能量化难度

这是整份代码里我最推荐你抄走的东西。第 1554 行 `botTarget` + 1578 行 `simulate`：

1. 用**固定种子的伪随机**（`mulberry32`）生成掉落物，同样的种子永远得到同样的序列。
2. 写一个「中等水平玩家」机器人：优先躲 0.5 秒内会砸到头的黑雾，否则去接最靠下的光屑。
3. 不开渲染，纯逻辑跑完七夜（约 3000 步），输出每夜的得分、剩余灯芯、接光数、触雾数。
4. 同时跑两个对照组：**第一夜站着不动**（应该能过，新手友好）、**第七夜满级站着不动**（必须输）。

翻到我最初的三次结果（都记录在案）：

| 版本 | 机器人成绩 | 判定的问题 |
| --- | --- | --- |
| v1 无追光 | 七夜全胜，第 5 夜就三轨满级 | 太简单，升级没有取舍 |
| v2 全程追光 | 第 4 夜起全 LOSE，触雾 5 次 | 太狠，人类也躲不掉 |
| v3 中段追光 + 最后一刻闪身 | 七夜全胜，第 4/5 夜只剩 2 灯芯，第七夜不动必输 | 通过 |

你在浏览器地址后加 `?selftest=1` 就能自己跑一遍，结果用绿色字直接印在页面左上角。

**为什么这招值得学**：难度调平靠手感试玩，一次至少 20 分钟；靠机器人，一次 3 秒。
你不需要它判断「好不好玩」，但它能立刻告诉你「能不能过」。
